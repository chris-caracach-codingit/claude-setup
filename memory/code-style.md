# Code style

## React / TSX

- **Arrow-function consts, not `function` declarations** — for components and module-level helpers, including the default export: `const Foo = (props) => { ... }` with `export default Foo;` at the bottom.
- **Fragment shorthand `<>...</>`**, not an imported `Fragment`. When a `.map()` needs a `key`, extract a small component that returns `<>...</>` and put the key on the instance.

- **Text lives in `Typography`, not raw `p` / `div` / `span`.** When touching a portal view, move every text container to `<Typography as='p' | 'div' | 'h2'…>` with the right variant; keep a raw element only for a strict structural reason (`li`, `ul`, layout wrappers). Redundant `<span>` wrappers inside a Typography go too. (2026-09-16, ENG-5013 Seeding page: "avoid using div and p as text containers, move everything to Typography".)

## CSS / SCSS

- **Use `rem` for spacing**, not `px` (÷16: 4px→0.25rem, 8px→0.5rem). Idiomatic exceptions are fine: `1px` hairline borders, `1000px` pill radii.
- **Spacing is explicit, never inherited from element defaults.** `Typography` has `margin: 0`; a raw `<p>` keeps `base-type.css`'s 1rem bottom margin (`@repo/ui` `global.css` zeroes only `h1`–`h6`). So a Figma "32px" means a 2rem margin/gap you set yourself on a module class. Chris caught this on ENG-5013 Seeding (2026-09-16): gaps were 16px short because Claude assumed a base `p` margin.
- **Exception, `apps/pdf-report`: sizes in `pt`, read from Figma.** The PDF Figma file is a Letter artboard in points, so a Figma "14px" is `14pt` in CSS. Take every size from Figma, never from current CSS numerals or screen feel, and never do a blanket numeric conversion. **Why:** existing PDF numerals have unknown provenance; the same-numeral px→pt pass (ENG-4966) inflated text by 4/3 and dense static pages overflowed until every size was re-read from Figma (ENG-5088).

## Comments & references

- **No code comments** unless explicitly asked. No block comments, rationale paragraphs, or JSDoc explaining behavior. Prefer renaming/restructuring to make code self-explanatory. (Test descriptions and prompt-string literals aren't code comments — those are fine.)
- **The rule applies to brand-new files and packages too** — a new component/helper written from scratch starts comment-free; don't seed it with prop docs, docblocks, or CSS rationale (2026-09-03, ENG-4965: "remove the excessive comments, not everything needs to be explained" — prop JSDoc, a normalize-helper docblock, CSS rationale lines, and test comments all cut in one pass).
- **"Constraint" comments don't get a pass either.** A cross-file constraint (e.g. why a z-index value must exceed other components' values) still isn't worth a comment — Chris had it removed on ENG-4854 (2026-07-31, "Do not over-explain things"). Put that context in the PR body if it matters. Repeated 2026-08-03 (ENG-4856): a why-imperative-navigation rationale comment in apps/mobile App.tsx drew "let's not over-comment please" — removed entirely, not just trimmed. Existing comment density in apps/mobile does NOT license new comments. This holds repo-wide, not just apps/mobile: a heavily-commented sibling file is not precedent for commenting the new one (2026-08-17, ENG-4884 — rationale blocks got written next to `useSessionReplay.ts` partly because that file carries them). What survived that cleanup was one single-line note on a guard whose deletion causes a real bug (Segment can't unregister a middleware, so the once-per-instance ref guard looks like dead defensiveness). A one-liner on a genuine footgun is the ceiling, not a license.
- **This applies to CI/pipeline files too** (workflows, scripts, actions) — even though the repo's existing workflows are heavily commented, don't match that. Chris (2026-07-24, ENG-4827): "let's avoid over-commenting and over-explaining all the pipeline." At most a one-line note for a genuinely non-obvious constraint. Rationale for tool/approach choices is NOT that — it belongs in the PR body (Chris removed a "why expo-doctor was swapped" comment, 2026-07-24). Repeated 2026-07-28 ("avoid over-explaining and over-commenting") after Claude wrote multi-line rationale comments in config.ts / deploy.yml — the rule covers chat verbosity too, keep explanations tight.
- **Field/member docs on types and interfaces are still code comments.** Explaining what a new field means on an `interface`/`type` (or naming the scenario a test `describe` block covers) reads as documentation rather than rationale, but it gets cut the same way — pick a self-describing name instead. 2026-08-17 (ENG-4879): comments went onto new `SubMetricEvaluation` fields, a backend return-type's members, a response type, a `const` map, a predicate helper, and throughout a new unit-test file; Chris asked for all of it removed in one pass. Test `it(...)` descriptions carry the meaning fine on their own.
- Repeated 2026-10-13 (ENG-5107 backend): a 10-line JSDoc on a helper, two inline "why" notes, a `/** */` on a const and one on a compare helper all drew "reduce the amount of comments, code should be self-explanatory and use small comments". Kept: one single-line note on the atomic-reserve footgun. Default for new backend helpers is zero comments, same as portals.
- **No ticket references in code** (`ENG-XXXX`, `JIRA-123`) — not in comments, error messages, or logs, and not in `describe`/`it` names for new tests. They rot fast. Ticket IDs belong in commits and PRs. (Pre-existing ones in a file you're editing can stay — don't churn them.) Repeated 2026-09-22 (ENG-5040): a 30-line rebrand.css header with ticket refs, Figma provenance, a hook→style mapping table and "judgment call" notes, plus `ENG-5040:` prefixed comments in Main.tsx / layout.tsx / Heading.tsx, drew "I don't like the comments that reference a ticket or some timestamp". Everything but two one-line footgun notes was cut. Provenance and mapping rationale go in the PR body.
- **Flag ticket refs in reviews too.** When reviewing a teammate's PR, every new `ENG-XXXX` / Linear URL in code (comments, Playwright `annotation`, test names) is a review finding. Missed on #2777 (ENG-5193) on 2026-11-03 and Chris called it out: "You know, I hate that."
- **Migrations get the template JSDoc and nothing else.** No rationale for index naming, column ordering, or why an old index is dropped. On ENG-4870 (2026-08-11) Chris removed three separate comments in two migration files — "Do not add that temp index probe. Just the migration", then "No comments. Just the migration." Reviewer-facing rationale is NOT an exception to the no-comments rule, and neither is a marker for deliberately temporary code; both belong in the PR body or the Slack thread. Same ticket, 2026-08-18: rationale comments explaining *why* an `orderBy` tiebreaker exists (backend controller + shared query modifier) drew "let's avoid over commenting" — deleted outright. A subtle-correctness reason is not an exception; the diff is the fix, the PR body is the explanation.
- **TEMP-WRAPPER markers are the one required comment** (Chris, 2026-08-05, ENG-4858). Portal code that exists only for the mobile WebView wrapper (bridge helpers, `ReactNativeWebView` / `__tinyApp` checks, in-app-only behavior branches) gets a short comment starting with `TEMP-WRAPPER:`. **Why:** the wrapper is temporary; when the app goes truly native, everything declared in Results Portal purely for the wrapper is removed, and the marker makes that a mechanical sweep (`grep -r TEMP-WRAPPER apps/results-portal`) instead of archaeology. Not for things a native app still needs (e.g. the AASA / universal-links file). Wrapper-side code in `apps/mobile` needs no marker; the whole app dies together. The grep is the list of current sites.

## Backend

- **Map data in JS, not in SQL.** Shape response DTOs and fill defaults in TypeScript after the query, rather than with raw SQL expressions or `COALESCE` (ENG-5138).
- **No index migration to make a feature query viable.** If the query needs an index that doesn't exist, find an already-indexed path or drop the approach (ENG-5025: "if there's no index, we won't go that way"). See [[execution-guardrails]].

## Fixing bugs

- **Fix at the root, not with shims** — even when a shim is smaller/safer. Prefer explicit structural separation (fork/quarantine the legacy path under clear names, make the correct system canonical) over runtime-conditional indirection. Present the root fix first; offer stopgaps only when explicitly labeled as such.
